The sample is an exported vmp_target in lab_vmp.exe, protected with VMProtect 3.9.4. Every register assignment, constant, and address below belongs to this one generated VM, not to the version as a whole.

The method is to establish instruction effects, follow state, and verify transfers. Matching the expected printed text is a useful final check; it is not how a VM exit is identified.

Scope: the source and unprotected build were inspected; the protected function was traced from its entry stub to native code, then continued through the printing routine to its caller. That establishes one executed path, not every handler or path in the protector.

Protected SHA-256: a0a136fd756eb40c65761168d8936fa460e362ec42be9adde53cfc16e5e11436.

Where you are Outside the VM · the original, unprotected function

1. Begin with the actual program

The source function is:

EXPORT NOINLINE void vmp_target(void) {
    printf("Hello DALI !\n");
}

The unprotected compiler output is effectively:

; RVAs, relative to the executable's image base
1440  lea rcx, [address_of_string]  ; string at RVA 4000
1447  jmp puts_thunk               ; thunk at RVA 26C8

The compiler substituted puts for the constant-format printf. puts supplies the newline, so the stored string is Hello DALI ! without it. The final jmp is a tail call: it transfers to another function without pushing an additional return address. When puts returns, it returns directly to the caller of vmp_target.

This raises two different questions:

  1. When does the VM finish interpreting and resume native instructions?
  2. When does the entire function, including printing, finish?

They have different answers here. And void means no defined C return value: a number in RAX is a physical register value, not automatically a result.

Where you are Overview · the whole path at once

2. Overall execution flow

main calls exported vmp_target
    -> entry jump and obfuscated entry stub
    -> save native state and construct VM working state
    -> decode next bytecode operation and select handler
    -> execute handler; repeat decoding and dispatch
    -> exit handler materializes native state
    -> final RET transfers to the native puts thunk
    -> thunk JMPs to puts
    -> puts RETs to main

The VM interprets bytecode by dispatching to native x64 handlers. The processor still runs native x64; virtualization adds no new instruction set.

A VM exit here means leaving this software interpreter with a native execution context prepared. It is unrelated to a hardware hypervisor VM exit.

Where you are Preliminaries · no code has executed yet

3. Addresses and navigation

The recorded runtime base was 0x7FF638E10000. Thus exit-transfer RVA 0x21FAA was runtime VA 0x7FF638E31FAA. With IDA base 0x140000000, it is 0x140021FAA. ASLR can change the runtime base next launch; reuse RVAs only for the same binary.

Do not confuse an RVA with a file offset. Unpacked or generated runtime bytes may have no corresponding file bytes; never subtract the image base and call the result a file offset.

The protected export at RVA 1440 jumps to 27FAFC. The executed stub includes:

push rbx
pushfq
mov rbx, 3F8AB3AF09240D32h
not bl
mov rbx, 418D6190ECBC5713h
mov rbx, [rsp+8]
mov qword ptr [rsp+8], 26D3A714h
push qword ptr [rsp]
popfq
lea rsp, [rsp+8]
call entry_initializer             ; RVA 1D595

Let entry_rsp be RSP at the export, before these pushes. [entry_rsp] contains the return address in main.

push rbx subtracts eight from RSP and stores old RBX. pushfq subtracts another eight and stores flags. It does not save all registers. Now [rsp] holds flags and [rsp+8] holds old RBX.

The two constants loaded into RBX do not survive: the second overwrites the first, then mov rbx,[rsp+8] restores the original RBX. not bl changes only RBX's low byte and does not change flags. In this straight-line sequence its result is overwritten before use.

The next store replaces the saved RBX slot with 26D3A714h. push [rsp] duplicates the saved flags; popfq consumes that duplicate. lea rsp,[rsp+8] discards the original flags slot without modifying arithmetic flags.

Immediately before the call:

RSP = entry_rsp - 8
[entry_rsp-8] = 26D3A714h
[entry_rsp]   = caller return address
RBX and the restorable saved flags have been restored

The call then pushes its own next-instruction address and transfers to the initializer. This is not simply an obfuscated sub rsp,8: it leaves a specific entry token in the allocated slot and then calls another location.

Single-step the stub and record RSP and the top three stack qwords after each instruction to confirm this.

Where you are VM initializer · building the interpreter's working state

5. Initialization: native registers become interpreter machinery

The initializer begins at RVA 1D595. It contains register saves, arithmetic, and calls to the immediately following instruction. Such a call $+5 still pushes a return address even though execution continues at the next instruction. Treating it as an ordinary helper call and stepping over it can miss its purpose.

Important executed instructions include:

1D5D1  mov rsi, relocation_delta
1D5E3  lea r10, [rsp+r10*2-48h]
1D5F2  lea rbp, [r10-230h]
1D604  and bpl, 0F0h
; more saves and entry-token calculations
1D6C4  mov rsp, rbp
1D6C7  mov rsi, r8
; more calculations
1D6F5  sub rsi, rbx

These are selected instructions, not a contiguous replacement for the initializer. Resolve their inputs from the trace before simplifying them. mov rsp,rbp is a stack pivot: the stack pointer moves to another prepared location.

The relocation delta in this run is runtime base minus preferred base. Arithmetic using it can turn preferred-image values into runtime addresses. It is different from the image base itself.

The reads, writes, and dispatch in this run support these roles:

Register Observed role in this interpreter path
R8 Bytecode cursor, or virtual instruction pointer (VIP)
R10 Virtual stack cursor (VSP), also used by restoration
RSI Evolving decoding-key state
R9 Handler-address accumulator/dispatch destination
RSP Native stack pointer, also used to address VM context storage

RSP is a real stack pointer and can also be a base for virtual-register storage. Changing RSP does not ask Windows to allocate memory; it selects locations within the available stack, subject to normal commitment/guard behavior.

The names R8 and R10 are evidence from this build, not universal VMProtect assignments. Identify a role from how values are used, not from a register's name.

Where you are VM initializer · workspace and stack setup

How the RBP setup differs from VMProtect 3.5

Mitch Zakocs' VMProtect 3.5.0.1274 analysis ends its de-obfuscated stack setup with these instructions (the register saves above them are omitted):

mov  r10, rsp                     ; r10 = stack pointer before allocation
sub  rsp, 180h                    ; reserve the VM workspace
and  rsp, 0FFFFFFFFFFFFFFF0h      ; align the register-space base to 16 bytes

So in 3.5 the workspace base is rsp itself, r10 is a snapshot of the stack pointer taken before the subtraction, and the alignment is a full-width and on rsp. Zakocs notes that rsp is the virtual register pointer in every VM he examined. rbp never appears in this setup: it is pushed for save/restore and otherwise acts as a general-purpose register (the first handler moves a popped virtual-stack value through rbp, and other VMs in the same binary use rbp as their virtual instruction pointer or encryption key).

This 3.9.4 sample builds the same kind of frame through rbp instead:

1D5E3  lea r10, [rsp+r10*2-48h]   ; derive the base from the native stack
1D5F2  lea rbp, [r10-230h]        ; compute the workspace base in rbp
1D604  and bpl, 0F0h              ; align rbp's low byte to 16 bytes
1D6C4  mov rsp, rbp               ; pivot the native stack onto that base

Resolved against this run's trace, the sequence does the following. The values are from the captured state, not from the mnemonic alone.

Instruction Effect in this run
lea r10, [rsp+r10*2-48h] r10 was 0, so r10 = rsp - 0x48. The r10*2 term is a real input; it disappeared only because r10 happened to be zero.
lea rbp, [r10-230h] rbp = r10 - 0x230 = rsp - 0x278. The workspace is not reserved with a sub rsp, imm.
and bpl, 0F0h Clears the low four bits of rbp, producing a 16-byte boundary. Here rbp was already aligned, so the value did not change.
mov rsp, rbp rsp takes the aligned base; rbp keeps the same value.

The concrete differences from 3.5 are:

Property VMProtect 3.5.0.1274 (Zakocs) This VMProtect 3.9.4 build
How the workspace is reserved sub rsp, 180h lea rbp, [r10-230h]
Register that becomes the base rsp rbp, then mov rsp, rbp copies it into rsp
Alignment instruction and rsp, 0FFFFFFFFFFFFFFF0h (64-bit operand) and bpl, 0F0h (8-bit operand on rbp)
Virtual stack pointer r10 = stack pointer before allocation r10 = rsp - 0x48, computed by lea
Base below the entry stack pointer 0x180 0x278 (0x48 to r10, then 0x230 to rbp)
Role of rbp saved scratch / per-VM context register the workspace base, still live after the pivot

Two consequences for analysis:

  • The classic prologue signature is gone. Searching for sub rsp, imm followed by and rsp, -16 will not find this build. The markers here are lea rbp, [r10-imm], an and on bpl, and mov rsp, rbp.
  • rbp is no longer a scratch register in the prologue. The initializer writes the base into rbp and leaves it there after the pivot, which is consistent with the restoration path later loading rbp back from the frame.

Treat the constants as build-specific evidence. Zakocs' comparison table shows the context registers are randomized per VM, and the 0x180 / 0x230 sizes and the choice of rbp are exactly what mutation changes between versions. Identify the setup by its data flow, not a fixed byte pattern.

Where you are VM initializer (another 3.9.4 sample) · stack setup

Another 3.9.4 sample: the same RBP reload hidden behind arithmetic

A different sample protected by the same 3.9.4 build opens its entry with a block that looks like dispatch setup but is not. Only the low parts of rbp change, and the result is a stack address:

push rbp
pushfq
mov rbp, 4288C3EF5303A0Fh
mov ebp, 0A05778Dh
neg bpl
shl bpl, 49h
not bp
mov rbp, [rsp+rbp*8-502C47F0h]
mov qword ptr [rsp+8], 7CE19025h
push qword ptr [rsp+0]
popfq
lea rsp, [rsp+8]
call loc_1400408B6

Let S be the value of rsp when the block begins. push rbp and pushfq save the original rbp and the flags, so [rsp] holds the saved flags, [rsp+8] holds the original rbp, and [rsp+16] holds the incoming stack top — the return address if the function was entered with a normal call. pushfq saves RFLAGS only; it does not save any general-purpose register.

The two constant loads do not create a handler base. Writing ebp clears the upper 32 bits of rbp on x86-64, so the second instruction discards the first value entirely: rbp = 0x000000000A05778D. The first mov is a dead store.

The three partial-register operations then compute the low bytes the load needs:

Instruction Effect Resulting rbp
neg bpl Negates the low byte: 0x8D becomes 0x73 0x0A057773
shl bpl, 49h Count is 0x49 & 0x1F = 9; shifting an 8-bit value left 9 places leaves zero 0x0A057700
not bp Flips the low 16 bits: 0x7700 becomes 0x88FF 0x0A0588FF

Substitute that value into the load:

rbp * 8                  = 0x502C47F8
0x502C47F8 - 0x502C47F0  = 0x8
mov rbp, [rsp+rbp*8-502C47F0h]  becomes  mov rbp, [rsp+8]

So the arithmetic does not select a handler. It computes the address of the saved rbp and reloads it. Removing any one of those three instructions breaks the address.

The block then reuses the now-free slot and adjusts the stack so the layout matches a plain adjustment:

  • mov qword ptr [rsp+8], 7CE19025h overwrites the saved-rbp slot with a constant. This is a stack write, not a data-section write; treat the constant as an encoded VM-entry parameter until the called code proves otherwise.
  • push qword ptr [rsp+0] followed by popfq restores the saved flags through a copy and leaves rsp unchanged. popfq restores flags, not general-purpose registers.
  • lea rsp, [rsp+8] moves rsp to S - 8 without reading memory and without touching flags, so it points at the constant.
  • call loc_1400408B6 pushes its own return address. At the destination, [rsp] is that return address, [rsp+8] is 0x7CE19025, and [rsp+16] is the original incoming stack top.

The net result is what sub rsp, 8 followed by a store and a call would produce, but the subtraction never appears. This is the same lesson as the workspace setup above: the frame is adjusted through pushes, a partial-register address calculation, and lea, so a recognizer that only looks for sub rsp, imm misses it. Whether loc_1400408B6 actually initializes the VM still has to be established from the code it reaches.

Where you are Dispatcher · decoding and selecting the next operation

6. Decoding and dispatch, with actual instructions

The first dispatch uses this subsequence:

1D700  lea r9, [address_at_RVA_1D6F8]
1D707  lea r8, [rbx+r8-2CA5h]
1D715  mov r11d, [r8+rbx-2CA1h]
1D71D  xor r11d, esi
1D727  dec r11d
1D734  not r11d
1D73E  ror r11d, 2
1D74F  xor r11d, 6D1F0835h
; key update and interleaved instructions omitted
1D78A  movsxd r11, r11d
1D792  add r9, r11
1D79B  jmp r9

At the relevant addressing operations RBX is 2CA1h: the LEA moves R8 back four bytes, and the load reads a dword at R8. XOR combines that dword with key state. DEC subtracts one; NOT flips bits; ROR rotates bits around within a 32-bit word. Arithmetic must be evaluated at the indicated width, wrapping modulo 2^32.

movsxd sign-extends a signed 32-bit displacement into 64 bits. Adding it to the address anchor produces the handler destination. The observed jump lands at RVA 20D7F4.

Red note — one jmp r9 is not "the dispatcher"

I found this by debugging, not by reading. A breakpoint on the jmp r9 above hit once, and then the whole VM ran to completion and printed its output. The reason is structural: as section 7 states, a handler mixes its virtual operation, dispatch machinery, and obfuscation. The block lea r9,…; add r9,r11; jmp r9 is therefore part of every handler, not one central routine. The address above is only the first copy (section 6), and the dispatch that reaches the exit is a different copy (section 11: "the preceding dispatch jumps to 21E8F").

So do not label a single address "the dispatcher." To catch every dispatch, trace and log the indirect-jump target (R9), or break on each copy — one address only covers the handler that owns it.

This resembles a switch-based interpreter in purpose, but there need not be an obvious opcode-number-to-handler array. Here decoded data contributes to a relative handler address. The decoding state also changes: a decoder that always uses the original key will soon produce incorrect destinations.

To generalize, work backward from the indirect jump: what produced its destination, what memory supplied the encoded value, and what state transformed it? Keep the destination expression and key-update expression separate.

Where you are Handler · executing one virtual operation

7. The first handler: extract an effect, not a visual pattern

The dispatch lands at RVA 20D7F4, a jump to 20D7F9 that loads the handler constant:

20D7F4  jmp 20D7F9
20D7F9  mov edx, 50376A2Dh
20D7FE  movsx ecx, dl
20D801  mov rdi, [r10+rdx-50376A2Dh]

Substitution reduces this to mov rdi,[r10]. That establishes a read from the virtual stack; it does not by itself establish that the cursor has advanced.

It reads an encoded byte near R8 and transforms AL:

20D809  movzx eax, byte ptr [r8+rcx-2Eh]
20D80F  xor al, sil
20D817  add al, 0
20D81E  not al
20D820  btr ebp, 1Fh
20D824  sbb al, 0B1h
20D829  neg al
20D82D  xor sil, al

At the byte read RCX is 2Dh, so the address is R8-1. The recorded byte is 63h; key low byte is 4Dh. The decoded values proceed 63 XOR 4D = 2E, NOT gives D1, subtracting B1 gives 20, and NEG gives E0.

Why does SBB subtract just B1 here? SBB also subtracts the carry flag. The preceding BTR puts the old bit 31 of EBP into carry; EBP is 4B95A48Ah, whose bit 31 is zero. This is an example where ignoring an apparently unrelated instruction breaks decoding reasoning.

Later:

20D83B  adc rax, rsp
20D846  mov [rdx+rax-2Dh], rdi

The trace shows RAX becomes RSP+E0h, and RDX is 2Dh, so the store writes the previously read value into context slot [context_base+E0h]. This supports a stack-to-context transfer effect. Establish the complete handler boundary and all cursor changes before giving it a complete virtual-opcode name.

The subsequent dword read and decoding prepare another handler destination. A native handler therefore mixes three concerns: its virtual operation, dispatch machinery, and obfuscation.

Where you are Dispatcher and handlers · recovery method

8. A reusable way to recover handlers

For each executed handler, maintain a ledger of: incoming VIP/VSP/key; memory reads; memory writes; outgoing VIP/VSP/key; and the next destination. Resolve effective addresses using the values at that exact instruction.

Track data dependencies: if a value influences a memory address, a store, a branch, decoding state, or eventual native state, it is relevant. A backward slice means tracing those dependencies backward from an effect. Include flags as dependencies: ADC and SBB use carry, conditional jumps use flags, and partial-register writes preserve some bits.

Only treat an instruction as ignorable after proving its effects are overwritten or irrelevant before use, including flag and memory effects. A trace proves what happened on one path. It does not prove another branch is impossible.

To reconstruct bytecode more generally, identify instruction operand widths, cursor direction, key evolution, and handler semantics. Explore additional paths with additional traces or symbolic reasoning. This sample's single simple path cannot reveal an entire protector instruction set.

Where you are Handler stream · searching for the VM exit

9. Find the exit without already knowing its address

Start x64dbg on the protected executable. Locate vmp_target through the export or use runtime image base plus 1440h after checking the file hash. Break there and record:

  • Thread identity, image base, and all registers.
  • Entry RSP, called entry_rsp, and the qword at [entry_rsp], called caller_return.
  • The memory map containing the code being entered.

For this run, entry_rsp was 94659FFA78h and caller_return was image base plus 274Eh. These are observations, not values to copy into another launch.

Step into the export's jump. The interpreter code traversed here lies in section .VI8, with RVA interval [14000h,27FDB4h). The end is exclusive. In another build obtain actual section bounds and determine which ranges contain VM execution; do not assume the same section name or boundaries.

Now trace individual instructions until execution leaves the suspected VM range. In x64dbg's command box, the following logs a compact pre-instruction state:

TraceSetLog "{p:cip}|{p:rsp}|{p:rax}|{p:rcx}|{i:cip}", 1
TraceSetLogFile "C:\temp\hello_trace.txt"
ticnd "cip < mod.main()+0x14000 || cip >= mod.main()+0x27FDB4", .100000

The trace-log file may be overwritten when a new trace starts; use a new filename when preserving an earlier run. Create the output directory first. Start this trace after entering the VM section; otherwise the condition is already true at the export. .100000 means decimal 100000 instructions. Stop if tracing reaches its limit; a limit stop is not evidence of an exit. Existing breakpoints or exceptions can also interrupt tracing.

At the stop, verify that the text log includes a final row for the current destination instruction. If it does not, append a row containing the current RIP/RSP/RAX/RCX and instruction using the same format, or compare the last logged instruction with the paused state manually. A boundary detector needs both sides of the transition.

This condition discovers candidates. Leaving a section could be a helper call, exception path, or another interpreter component. Conversely, native code may reside inside that same section. A range test reduces the search; it does not prove the interpretation has finished.

Use an uninterrupted trace of the same thread. Do not concatenate separate runs, filtered-out instruction sequences, or different threads and interpret adjacent rows as consecutive execution.

Where you are Analysis tooling · no execution

10. Small script to list those candidates

The script below reads either the compact format above or the 14-column full trace. It uses only the specified ranges and consecutive executed addresses; it has no embedded exit RVA or expected Hello DALI output.

The complete script is available as Download find_vm_transitions.py:

import argparse
import json
from pathlib import Path


def records(path):
    short = ('rip', 'rsp', 'rax', 'rcx')
    full = ('rip', 'rsp', 'rbp', 'rbx', 'rdi', 'r8', 'r9', 'r10',
            'r11', 'rax', 'rcx', 'rdx', 'rsi')
    for line_number, line in enumerate(Path(path).read_text(encoding='utf-8-sig').splitlines(), 1):
        if not line.strip():
            continue
        fields = line.split('|')
        names = short if len(fields) == 5 else full if len(fields) == 14 else None
        if names is None:
            raise ValueError(f'Line {line_number}: expected 5 or 14 columns')
        try:
            state = dict(zip(names, (int(s.strip(), 16) for s in fields[:-1])))
        except ValueError as exc:
            raise ValueError(f'Line {line_number}: invalid hexadecimal register') from exc
        yield state, fields[-1].strip(), line_number


def find(path, base, ranges):
    def inside(va):
        return any(lo <= va - base < hi for lo, hi in ranges)
    previous = None
    for current in records(path):
        if previous and inside(previous[0]['rip']) and not inside(current[0]['rip']):
            before, instruction, line = previous
            after = current[0]
            yield {
                'classification': 'range departure; manual verification required',
                'source_line': line,
                'transfer_va': hex(before['rip']),
                'transfer_rva': hex(before['rip'] - base),
                'instruction': instruction,
                'destination_va': hex(after['rip']),
                'destination_minus_main_base': hex(after['rip'] - base),
                'rsp_delta': after['rsp'] - before['rsp'],
                'destination_registers': {k: hex(v) for k, v in after.items()},
            }
        previous = current


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument('trace')
    parser.add_argument('--base', required=True, type=lambda s: int(s, 0))
    parser.add_argument('--vm-range', required=True, action='append', metavar='0xSTART:0xEND')
    args = parser.parse_args()
    ranges = [tuple(int(v, 0) for v in s.split(':')) for s in args.vm_range]
    if any(len(r) != 2 or r[0] < 0 or r[0] >= r[1] for r in ranges):
        parser.error('Each range must contain increasing, nonnegative START:END RVAs')
    print(json.dumps(list(find(args.trace, args.base, ranges)), indent=2))


if __name__ == '__main__':
    main()

Where you are VM exit · the restoration handler

11. Prove this candidate is a VM exit

Follow the trace backward from 21FAA. The preceding dispatch jumps to 21E8F, where this restoration sequence begins:

21E8F  mov eax, 4032A1A7h
21E94  mov rsp, r10
21E97  pop rbx
21E98  call next_instruction
21E9D  mov r8, [rsp+rax-4032A19Fh]
; further loads reconstruct native register state

At the pivot, RSP changes from VM workspace 94659FF7C0h to frame base frame_base = 94659FF9F0h. POP RBX advances it by eight; CALL-next pushes a code address and moves it back to frame_base. At the shown R8 load, the index expression is 4032A1A7h-4032A19Fh = 8, so it reads [frame_base+8].

Do not demand a clean run of POP instructions. This exit uses indexed MOV loads, temporary stack movement, and interleaved arithmetic.

Later, with RCX=FFA7h:

21F63  mov rcx, [rsp+rcx*4-3FE44h]

The offset reduces to 58h; this reconstructs native RCX from [frame_base+58h]. It becomes the string pointer at image base plus 4000h, the argument required by native puts under the Windows x64 calling convention.

The tail includes:

21F73  push qword ptr [rsp+60h]
21F77  popfq
; flag-preserving instructions and further register restoration
21F8B  mov r14, [rsp+rdx-FF3Eh]
21F93  mov rdi, [rsp+rdx-FF36h]
21F9B  not edx
21F9D  mov rdx, [rsp+78h]
21FA2  lea rsp, [rsp+80h]
21FAA  ret

With RDX=FFA6h at the relevant indexed loads, R14 comes from [frame_base+68h] and RDI from [frame_base+70h]. The final LEA sets RSP to frame_base+80h = entry_rsp-8. RET consumes a qword destination and increments RSP by eight, leaving RSP=entry_rsp at native continuation.

The chain: a VM dispatch reaches this block, the block pivots away from VM workspace and reconstructs native state, its final transfer reaches ordinary native code, and the stack suits that continuation. Together these establish the exit on this path — a RET alone would not.

An exit handler is a block or path of code. Its final transfer is one instruction. The continuation is the instruction reached by that transfer. A function return is another semantic boundary and can occur later, as it does here.

Caller versus callee: main is the caller of vmp_target; puts is the callee reached by its tail call. A continuation is simply where execution proceeds next. The puts thunk is the native continuation after the VM exit; the instruction in main is the caller continuation after the whole invocation finishes. Reaching puts alone does not establish a VM exit: the preceding restoration and transfer are the evidence.

Where you are Manual method · applies to any protected binary

13A. General manual method: use this on another protected binary

Keep the sample addresses in section 12 as a worked example. On another binary, discover the corresponding locations using the steps below. VMProtect 3.9.4 does not imply one fixed exit signature, register assignment, or section layout. This is an investigation method, not a guarantee that every binary yields to one breakpoint or search.

Step 1 — Identify the target function

In IDA, start with its export if one exists. Otherwise find a caller, a relevant string reference, or another known program operation and work toward the function implementing it. An export may point to a forwarding stub, so follow the instructions rather than assuming the export is the interpreter itself.

Press G to navigate to an address, and X to inspect an address or operand's cross-references. An indirect jump may have no useful static cross-reference because its destination is calculated at runtime. IDA navigation reference.

Example: this sample exports vmp_target at RVA 1440, which jumps to RVA 27FAFC. Those are two locations with different purposes: the function's public entry and its entry stub.

If packing hides the real instructions on disk, pause after they have become executable at runtime and inspect those live bytes. An IDA database opened from the original file may not show the same instructions as the running process. Resolve that difference before trusting a static listing.

Step 2 — Stop at the function entry and make a baseline

In x64dbg, resolve the executable's current base in the memory map or module view. Add the function RVA to that base. Set a breakpoint at the resulting address and run until this invocation reaches it.

For this sample, the command is:

bp mod.main()+0x1440

For a different executable, replace 0x1440 with its discovered function RVA. For a DLL, use that DLL's base instead of the main executable's base. x64dbg breakpoint reference.

Before stepping, write down the current thread, register values, and RSP. Call this initial RSP entry_rsp. Inspect the eight-byte value at [entry_rsp]. For an ordinary function entered by CALL, it is the caller's continuation address; call it caller_return. Confirm caller_return points to plausible caller code after the call. Do not apply that assumption blindly to a program entry point, exception entry, or internal region reached by a jump.

This baseline supports two separate questions later: whether a usable native context was recovered, and whether this function invocation finished. It does not imply every exit register must equal its entry value: the function can change its result, arguments for a native call, and other allowed state.

Example: this sample's C has RVA 274E. Its numeric VA changes with the runtime image base. The stack addresses change between runs too.

Step 3 — Follow entry into the interpreter

Use Step Into, one instruction at a time, while examining entry. x64dbg also exposes this as the sti command. Step Into reference.

Look for a combination of register saves, a stack/workspace setup, reads from encoded instruction data, and repeated calculated transfers to blocks implementing operations. No single PUSH or indirect JMP proves virtualization.

Do not use “run until return” as your discovery method. Obfuscated code can use RET as an internal jump, and CALL/RET as stack operations. Step-over can likewise skip details you need, particularly CALL-next sequences.

Example: the entry eventually prepares R8 as a bytecode cursor, R10 as a virtual stack cursor, and RSI as decoding state. In another build the same roles may use other registers or memory slots. Keep provisional labels until repeated behavior supports them.

Step 4 — Choose a way to locate a possible transition

The question is: where does this interpreter prepare machine state for ordinary native execution? You can approach it in two ways.

Execution-first approach: trace from the protected entry, preserving every executed instruction in the thread. If interpreter execution occupies identifiable ranges, use a range-departure condition as in section 9 to stop at a candidate. Obtain the ranges from the actual code and memory map. A section boundary is a convenient filter, not the definition of a VM boundary.

Example: the range filter finds the transition from 21FAA to 26C8. It does not use the string or the expected console output.

If the interpreter and native code share a section, the filter can miss the exit. Instead, look in the trace for a cluster of loads that reconstruct registers, a switch from VM workspace to a continuation stack, and a transfer into normal native work. You can also pause at a known native routine reached by the target and read the already-recorded path into it; scrolling backward in disassembly cannot recover instructions that were never recorded.

IDA-first approach: inspect possible restoration blocks in the disassembly. Search for combinations such as RSP being assigned from another register, loads into several native registers from a common frame, restoration of flags, and a final indirect transfer. Look beyond clean POP sequences: indexed MOV instructions may implement the same effect. Treat these as candidates and set execution breakpoints to determine whether your target reaches them.

Searching all RET instructions is usually too broad. Searching only popfq; ret is usually too narrow. Xrefs may reveal callers of a block, but missing xrefs do not prove it is unreachable. For this reason, IDA-only analysis often stops at a candidate when destinations or memory contents are determined at runtime.

Step 5 — Inspect the instructions before the candidate transfer

Work backward in the recorded execution path and identify which instructions supplied the final register values and stack pointer. “Backward” means earlier executed instructions, not necessarily lower addresses.

For each memory load, calculate the effective address using the register values at that instruction. Ask whether several loads retrieve values from one saved or VM-produced context. Watch for registers loaded temporarily and overwritten again: only the final live values matter at the transfer.

Example:

; at RVA 21E9D in this sample
mov r8, [rsp+rax-4032A19Fh]

With RAX=4032A1A7h, this reads [rsp+8]. It is a straightforward context load hidden behind an index expression. The presence of the large constant is not the important feature; the resolved memory access is.

The register values may represent the state after virtual instructions have changed it. “Restoration” therefore means materializing the native state required by the continuation, not necessarily restoring every original entry value.

Step 6 — Prove what the final transfer does

Place a breakpoint on the candidate's last transfer and inspect it before executing it.

For a plain RET, read the qword at [rsp]. That is the destination it will consume. Step once and check that RIP becomes that value and RSP increases by eight. A ret imm16 additionally adjusts RSP by its immediate amount.

For JMP register, read that register and step once. For JMP [memory], read the destination pointer from the specified memory location.

For CALL, account for the extra return address it pushes. It may be a native helper called by the interpreter rather than an exit. Follow what happens when the helper returns before classifying the transition.

Example: before the RET at RVA 21FAA, RSP=entry_rsp-8 and [rsp] points to RVA 26C8. After stepping, RIP is the thunk and RSP=entry_rsp. This describes exactly how the VM hands control to native code.

Do not assume every protector transition must end in RET. If exceptions or other unusual transfers are involved, follow their actual context changes rather than forcing the RET model onto them.

Step 7 — Verify the destination's meaning

At the destination, inspect the next instructions, their arguments, and the stack. Do they consume a coherent native calling context? Has interpreter dispatch stopped? Does execution later re-enter the interpreter?

A native helper call made while the VM's working context remains active is different from a transition that materializes the protected program's native state. A verified exit can also be temporary: the program may execute native instructions and later enter another virtualized region. Neither observation alone proves the entire function is finished.

Example: the destination at RVA 26C8 forwards to puts. RCX holds its string argument; [rsp] holds the original caller continuation. The VM has finished this region, but puts has not yet printed anything at the moment of capture.

Step 8 — Capture the right state

To capture post-VM native state, stop at the verified continuation before its first instruction executes. Record the registers and relevant memory there. For this sample that is RVA 26C8.

To capture the function's return, use the caller continuation caller_return recorded at entry, and inspect state before the caller changes it. Verify that it is the same invocation and thread. Recursion and repeated calls can reach the same address many times, so an address-only breakpoint may need a thread/stack condition or manual invocation tracking.

Example: caller_return is RVA 274E; its first instruction clears EAX. Read the register before executing that instruction. This function is void, so the value is not a defined C return value even though a library result happens to be visible.

For other functions, use the signature and calling convention to decide where a return value resides. RAX is not a universal return-value container.

Step 9 — Move the verified finding back into IDA

Compute RVA = runtime address - owning module's runtime base. Navigate to IDA image base + RVA with G. For the final transfer, 0x140000000 + 0x21FAA = 0x140021FAA.

Comment three separate locations: the restoration handler, the final transfer, and the native continuation. Record the binary hash and how you verified the path. This makes the analysis reproducible and avoids naming the whole handler, its RET, and its destination all “vmexit” without distinction.

If you use IDA's debugger instead of x64dbg, the same experiment applies: select an appropriate debugger, launch the target, resolve loaded-module addresses, break at the target entry, inspect registers/stack, step through the candidate transfer, and verify its destination. Static IDA views alone cannot display live register values. Account for any database rebasing when switching between static and runtime addresses.

What counts as a convincing explanation?

A convincing explanation shows: “This path belongs to the interpreter. These instructions prepare the native registers and stack. This instruction transfers to this destination. The destination consumes that state as native code. Here is where the function later returns, if that is a separate event.”

That explanation transfers between binaries. The sample RVAs are concrete examples, while the evidence chain is what carries over to another VMProtect build.

First, clarify “all virtual registers returned to real registers”

A VM can have more memory slots than the CPU has registers. Some slots represent native registers, some hold intermediate values, and others contain interpreter bookkeeping. There is no general one-to-one copy of all virtual registers to hardware registers.

The exit materializes the native context required at the continuation. Here, loads can be identified for all fifteen general-purpose registers other than RSP, an RSP adjustment, and a flags restoration; RET establishes RIP. That claim is about this sequence only — it does not cover XMM registers or all architectural state, nor prove every restored value equals the original entry value.

Check E — Distinguish VM completion from function completion

Run to caller_return, recorded at function entry. In this build caller_return is RVA 274E. At that stop, puts has returned, and RSP should be entry_rsp+8 on this normal path. The waiting caller instruction is xor eax,eax.

Capture before that XOR to inspect the raw library result. The recorded result was RAX=0, but vmp_target is void, and another successful puts implementation need not return exactly zero.

The boundary is now accounted for: the loads above reconstruct native register state, RET transfers to the puts thunk with the original caller address still on the stack, and puts later returns to that caller. This verifies the observed region's exit without claiming that every VM temporary, machine-state component, or path has been recovered.

14. Exactly where to capture registers and the result

For the state after the virtualized region, capture at the first native continuation before its instruction executes. Here that is RVA 26C8. Capturing at the final RET gives restored general registers but the pre-transfer RSP and RIP. Capturing after RET gives the continuation's actual RSP/RIP too.

In the recorded run, at 26C8:

RSP = entry_rsp
RCX = image_base + 4000h
RAX = 1

RAX=1 here is not the result of printing: puts has not run. At the caller continuation 274E, after puts finished, raw RAX was 0 in this execution. That is an observed implementation result, not a promised value for every CRT. puts indicates success with a nonnegative result; it does not promise the character count.

Because vmp_target is void, neither capture is a defined return value of vmp_target. For a variant with a defined integer result, change the source to int vmp_target(void) { return puts("Hello DALI !"); }, rebuild, reprotect, and repeat discovery. Its code layout may change.

Return values after the exit

Only when that exit has already established the final integer result. A VM exit that resumes more native computation may occur before the result is ready. Break at the caller continuation to inspect the final result of a normally returning function, before the caller overwrites it.

For a Windows x64 function returning a 32-bit int, interpret EAX. Do not assign meaning to unused upper bits merely because the debugger displays the whole RAX. The calling convention specifies return locations and which registers a callee must preserve. Microsoft x64 calling convention.

Restored state is not necessarily entry state. At an internal VM exit, registers must contain what the protected code needs at that continuation. At a normal function return, nonvolatile registers must satisfy the calling convention; volatile registers can have changed. Comparing every register with entry and demanding equality would reject valid exits. In this sample RCX deliberately becomes the puts argument.

For other targets, identify the function's signature and ABI first. Integer results commonly use RAX/EAX; floating-point results use XMM0; some aggregate returns use caller-provided memory. This trace logs selected general registers, not XMM state, all flags, or memory writes. A full capture needs the relevant additional state. Debugger stepping can also affect how trap-related flag bits appear.

15. Detection rules and their limits

Observation Useful inference Failure case
Execution leaves known VM ranges Investigate this transfer Native helper, another VM section, exception path
Many native registers loaded from a frame Possible context restoration Ordinary epilogue or context-switch code
RSP pivots from VM workspace Possible restoration phase Internal VM stack management
POPFQ near restoration Flags being materialized Entry code or unrelated flag management
Final RET/JMP reaches native code with coherent stack/arguments Stronger exit evidence A temporary native excursion may return to VM
Original caller continuation is reached This invocation finished on that path Does not locate the earlier VM boundary

Do not hardcode a register order, a section name, a POP count, or one terminal opcode as a universal signature. The strongest reusable rule is semantic: trace a transition out of interpretation, demonstrate how native state was prepared, and verify what consumes that state.

Static analysis can decode available bytes, examine exports/imports, propagate constants, and propose control-flow and restoration candidates. Execution resolves this run's indirect destinations, decrypted bytes, register-dependent addresses, and actual stack state. Packing makes runtime observation particularly useful, but execution is still path-limited.

For this exact file, one exit to a native tail-call continuation was verified. This does not establish every possible exit, a complete bytecode grammar, all exception behavior, or all VMProtect 3.9.4 variants. New builds require new evidence even when the source is unchanged.
